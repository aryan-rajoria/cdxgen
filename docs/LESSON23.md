# Lesson 23 - Exploring BOMs interactively with the cdxi REPL

A BOM is a dense JSON document. Flattening 800 components, a dependency graph,
formulation data, and audit annotations into grep commands is slow and
error-prone. `cdxi` is the interactive shell that cdxgen ships for exploring
BOMs without writing one-off scripts. You load a BOM, then use dot-commands to
pivot through dependencies, services, evidence, provenance, and audit
findings.

## Goal

By the end of this lesson you should be able to answer:

1. How do I start cdxi and load a BOM (or generate one inline)?
2. What are the core navigation commands for dependencies, components, and
   services?
3. How do I inspect a single component in detail, including evidence and
   formulation data?
4. What specialized pivots exist for Go Evinse, Cargo, OBOM, and audit
   workflows?
5. How does cdxi help with triage across large BOMs?

## Prerequisites

- Node.js >= 24 (the v13 floor)
- `@cdxgen/cdxgen` installed globally. The REPL binary is called `cdxi`:

```shell
npm install -g @cdxgen/cdxgen
```

## Step 1: Starting cdxi and loading a BOM

Start the REPL with no arguments. If `bom.json` exists in the current
directory, cdxi imports it automatically:

```shell
cdxi
```

Pass a BOM file as an argument to import it immediately, or use `.import`
inside a session:

```shell
cdxi bom.json
```

```text
cdx ↝ .import bom.json
cdx ↝ .import bom.evinse.json
cdx ↝ .import bom.cdx
cdx ↝ .import ghcr.io/owner/repo
```

cdxi accepts CycloneDX JSON, SPDX JSON-LD (converted to a CycloneDX-like view
on the fly), protobuf `.cdx` / `.proto` binaries, and OCI references like
`ghcr.io/...` when a CycloneDX attachment is present.

To generate a BOM from a local project without leaving the REPL, use
`.create`:

```text
cdx ↝ .create .
```

When you import a BOM, cdxi detects its type and suggests relevant commands.
Importing an OBOM hints at `.osinfocategories`. Importing a Cargo BOM suggests
`.cargohotspots`. Importing a Golem-enriched BOM suggests `.golemsummary`.

## Step 2: Core navigation commands

Once a BOM is loaded, start with `.summary` for a high-level overview:

```text
cdx ↝ .summary
cdx ↝ .print
cdx ↝ .tree
```

`.print` renders the full component list as a table. `.tree` shows the
dependency graph rooted at the metadata component. For SaaSBOMs, `.services`
lists services and `.provides` shows the provides tree.

### Searching and querying

cdxi has a built-in case-insensitive search across component names,
descriptions, publishers, purls, and tags:

```text
cdx ↝ .search spring
```

For raw power, `.query` runs a JSONata expression directly against the loaded
BOM. This is the escape hatch when no dot-command covers your question:

```text
cdx ↝ .query components[name ~> /lodash/i]
cdx ↝ .query $count(components)
```

Sort the component table by any field: `.sort name`.

## Step 3: Inspection pivots

### Inspecting a single component

`.inspect` prints the full JSON for a component matching a name or purl
fragment. This is the fastest way to see all properties, hashes, licenses, and
evidence for one package:

```text
cdx ↝ .inspect lodash
cdx ↝ .inspect pkg:npm/express@4.18.2
```

### Evidence and formulation

If you loaded an enriched BOM (generated by `evinse`), pivot through the
evidence sections:

```text
cdx ↝ .occurrences
cdx ↝ .callstack
cdx ↝ .formulation
```

`.occurrences` shows components with `evidence.occurrences` (where a package
was found in the source tree). `.callstack` shows call-stack evidence.
`.formulation` renders build formulation data (CI workflows, build tools,
tasks).

### Provenance, trust, and audit findings

```text
cdx ↝ .trusted
cdx ↝ .provenance
cdx ↝ .auditfindings
cdx ↝ .auditactions
cdx ↝ .dispatchedges
```

`.trusted` lists components with trusted-publishing metadata.
`.provenance` lists components with direct registry provenance evidence.
`.auditfindings` summarizes all `cdx:audit:*` annotations from `--bom-audit`
or `cdx-audit`. `.auditactions` extracts just the next-action and
upstream-guidance fields. `.dispatchedges` shows correlated
sender-to-receiver workflow edges captured by predictive audit, which are
among the strongest supply-chain incident signals.

For VDR files, `.vulnerabilities` lists the vulnerability entries. `.licenses`
renders a visual license distribution chart, useful for spotting GPL or
unknown-license concentrations.

## Step 4: Specialized pivots

cdxi auto-detects BOM flavors and offers specialized views.

### Go Evinse and Golem

When you import a BOM generated by `evinse -l go`, cdxi detects `cdx:golem:*`
properties and suggests the Golem pivots:

```text
cdx ↝ .golemsummary
cdx ↝ .golemhotspots
cdx ↝ .golemcoverage
cdx ↝ .golemtips
```

`.golemsummary` prints a key-value table with tool version, call graph mode,
package and module counts, usage scopes, build directives, security signal
categories, and evidence coverage counts. `.golemhotspots` filters to
components with security signals, local replacements, private module
candidates, or vendored modules. `.golemcoverage` filters to components with
occurrence, scope, or call-stack evidence.

### Cargo hotspots and workflows

For Cargo BOMs generated with `--include-formulation`:

```text
cdx ↝ .cargohotspots
cdx ↝ .cargoworkflows
```

`.cargohotspots` surfaces yanked crates, git or path sources, build-only
workspace helpers, and target-specific dependencies. `.cargoworkflows` shows
Cargo-native formulation entries alongside Cargo-related GitHub Actions and
run steps.

### OBOM categories

For operating-system BOMs, cdxi dynamically defines a dot-command for each
osquery category present in the BOM:

```text
cdx ↝ .osinfocategories
cdx ↝ .processes
cdx ↝ .services_snapshot
cdx ↝ .scheduled_tasks
cdx ↝ .listening_ports
cdx ↝ .obomtips
```

`.osinfocategories` lists the available category names so you know which
dot-commands are valid for the loaded OBOM.

### Crypto and unpackaged files

```text
cdx ↝ .cryptos
cdx ↝ .sourcecryptos
cdx ↝ .unpackagedbins
cdx ↝ .unpackagedlibs
cdx ↝ .instrumented
```

`.cryptos` shows `cryptographic-asset` components. `.sourcecryptos` narrows to
source-derived crypto algorithms from AST analysis. `.unpackagedbins` and
`.unpackagedlibs` show file components not traced back to OS package ownership,
useful for container and rootfs triage. `.instrumented` shows dynamically
instrumented libraries with verification evidence.

## Step 5: A realistic triage session

Here is a practical session exploring a Node.js SBOM enriched with audit
annotations:

```text
$ cdxi bom.json

cdx ↝ .summary
# Component count, dependency count, tools, metadata

cdx ↝ .auditfindings
# Table: Engine | Severity | Rule | Target | Next action

cdx ↝ .trusted
# Components backed by trusted publishing

cdx ↝ .search fetch
# Finds components matching "fetch"

cdx ↝ .inspect node-fetch
# Full JSON for the node-fetch component

cdx ↝ .tree
# Dependency graph rooted at the metadata component

cdx ↝ .licenses
# License distribution chart

cdx ↝ .query components[$count(evidence.occurrences) > 3]
# Components with strong source correlation

cdx ↝ .validate
# Validates against the CycloneDX JSON schema

cdx ↝ .save bom-reviewed.json
cdx ↝ .exit
```

This session moves from a high-level summary, through targeted audit findings,
to individual component inspection, and finishes by validating and saving the
BOM. Each pivot takes seconds.

### Tips for large BOMs

- Use `.search` first to narrow to a package family, then `.inspect` to drill
  in.
- `.query` with JSONata is the most flexible pivot. For example, to list all
  components missing a license: `.query components[$count(licenses) = 0].name`
- `.update` can modify components with a JSONata update expression, but use it
  carefully since it mutates the in-memory BOM. The result is only persisted
  when you run `.save`.

## What to take away

1. Start with `cdxi bom.json` or `.import` inside a session. cdxi accepts
   CycloneDX JSON, SPDX JSON-LD, protobuf, and OCI references.
2. `.summary`, `.print`, and `.tree` are the core navigation commands.
   `.search` and `.query` (JSONata) cover anything the dot-commands do not.
3. `.inspect` gives you the full JSON for one component. `.occurrences`,
   `.callstack`, and `.formulation` pivot through evidence sections.
4. Specialized pivots (`.golemsummary`, `.cargohotspots`, `.osinfocategories`,
   `.auditfindings`) are auto-suggested based on BOM flavor, so you do not need
   to memorize them all.
5. cdxi is built for interactive triage. For automation, use `cdx-audit
--report json` or `jq` directly against the BOM file.
